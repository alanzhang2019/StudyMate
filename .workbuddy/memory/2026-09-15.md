## B站 space 接口突破 412 风控，10 个课题换用官方中文字幕版视频（commit 0fa9f95，已 push）

### 背景

该 UP 主主页：`https://space.bilibili.com/3546677931674532`

### 关键突破：WBI 签名 + 登录 cookie

**问题**：B站 space 页有登录墙，headless 抓取只能拿到「登录后你可以：TA的视频」；
所有 space 相关接口（`space/wbi/arc/search`、`space/arc/search`、`series/recArchivesByKeywords`）
一律返回 **412 Precondition Failed**；`acc/info` 报 `-799`；关键词搜索该 mid 命中 0 条。

**解法**（两步，缺一不可）：

1. **WBI 签名**：nav 接口取 `wbi_img.img_url` / `sub_url` → 各取文件名 → 拼成 64 字符
   → 按 `MIXIN_KEY_ENC_TAB` 重排取前 32 位 = `mixin_key`
   → 请求参数按 key 排序 urlencode + `wts=时间戳` + mixin_key 求 md5 = `w_rid`
2. **登录 cookie**：`SESSDATA` + `bili_jct` + `buvid3` + `DedeUserID`

**脚本**（均在 `.workbuddy/bili/`，该目录已 gitignore）：
- `extract_cookies.py` —— Chrome/Edge cookie 解密（见下）
- `fetch_uploader.py` —— WBI 签名拉 UP 主视频列表
- `bili-cookies.json` / `cookies.txt`（Netscape 格式，供 yt-dlp `--cookies`）

### Chrome cookie 解密（Windows）

1. 从 `Local State` 的 `os_crypt.encrypted_key` 取 DPAPI blob，**去掉前 5 字节 `DPAPI` 前缀**
2. `CryptUnprotectData` 得 AES 主密钥
3. cookie 值格式 = `v10`/`v11` + 12B nonce + ciphertext + 16B tag，用 **AES-256-GCM** 解密

**坑**：
- **Chromium cookie DB 有独占锁**：浏览器运行时 `cp` 报 `Device or resource busy`；
  Python 直读 `Permission denied`；SQLite 只读 URI 也打不开；Win32 `CreateFileW`
  带 `FILE_SHARE_*` 返回 `err=32`。**解法：`shutil.copy2` 快照到临时文件后只读打开。**
- **Chrome 真实库在 `Default/Network/Cookies`**（约 327KB）；`Default/Cookies` 是 0 字节空壳。
- 解出 20 个 cookie，`SESSDATA` 长度 222，登录 UID `2056211255`。

**format id 必须手写**：B站 H.264(avc1) 与 HEVC(hvc1) 分开编号。

- 用 `-f "bv*[height<=720]+ba/b"` 会匹配到 hvc1，**必须指定具体 id 或加 `[vcodec^=avc]`**

## 生产事故：作品墙 HTTP 500（2026-09-15）

### 现象

用户截图报 `https://aijiangti.cn/camp/works` 显示「作品加载失败：HTTP 500」。

### 真因（logs 里只有这一行）

```
SqliteError: no such column: viewCount
```

### 根因机制（这条最值得记）

`frontend/lib/db.ts` 的 init block 里，`CREATE INDEX idx_camp_works_hot ON camp_works (status, viewCount DESC, ...)`
与 `CREATE TABLE IF NOT EXISTS camp_works` **处于同一个 `_db.exec()` 批次**。

链路：老库 `camp_works` 已存在 → `CREATE TABLE IF NOT EXISTS` **整条跳过**（不会补新列）
→ `viewCount` 仍不存在 → `CREATE INDEX` 引用它 → 抛错
→ **`db.exec()` 多语句批次是「全有或全无」，整批中断**
→ 其后**所有**补列 `ALTER TABLE ADD COLUMN` 全部不执行。

结果：不仅 `viewCount` 没补上，**该批次之后的迁移全部静默失效**。
再加上错误被空 `catch { /* column already exists */ }` 吞掉 → 日志无痕
→ 潜伏到用户访问作品墙才爆发。

### 应急 vs 根治

* **应急**（已执行）：线上库手工 `ALTER TABLE camp_works ADD COLUMN viewCount INTEGER NOT NULL DEFAULT 0`
  → API **立即恢复 200**，10 个作品数据完整（重启容器验证过持久性）
* **根治**：commit `b732cb2`，见下

### 根治内容

1. `idx_camp_works_hot` 移出 init 批次，**下沉到 `applyMigrations`**，确保晚于补列执行
2. 新增 `migrate(db, sql, label)` helper：`already exists` / `duplicate column name` 静默跳过，
   **其余错误 `console.error`**（区分「幂等跳过」与「真失败」）
3. **16 处**补列/建索引全改 `migrate()`（usage_events.visitorId、users.name/role、csp_progress 2 列、
   mistake_book 10 列、camp_works 各列、2 个索引）
4. `applyMigrations` 的 `throw err` 改 `console.error` —— 不让一批失败拖垮后续全部
5. `camp_works.studentId` **`NOT NULL` → 可空**（2 处 schema），学生可匿名提交，根治重建迁移触发条件
6. 表重建迁移改 **`PRAGMA table_info` 动态取列**，源表缺列时自动裁剪 SELECT，`viewCount` 做 `COALESCE`
7. 重建迁移 catch 补日志 + 手动恢复指引（`ALTER TABLE camp_works_old RENAME TO camp_works`）
8. `applyMigrations` 末尾**启动自检**：`viewCount/grade/htmlFile/editToken/coverSource` 缺任一即打 error

### 关键知识点

* **SQLite `CREATE TABLE IF NOT EXISTS` 表已存在时整条跳过，不会补列** → 老库必须靠 `ALTER TABLE ADD COLUMN`
* **`db.exec()` 多语句批次是「全有或全无」**：批次内任一语句抛错，其后所有语句都不执行
* **`getDb()` 是双层迁移结构**：
  * init block（`if (!_dbInit || !tableExists(...))` 门控）→ **开过一次就不再跑**
  * `applyMigrations(_db)` → **每次 `getDb()` 都跑**，负责给老库补列。补列逻辑必须放这里
* **`PRAGMA table_info()` 读源表列必须在 `RENAME` 之前**（`camp_works_old` 要 RENAME 后才存在）
* **WAL 模式**：判「库最近改了什么」看 `-wal` 文件时间，主库文件时间戳会滞后

### 二、视频预加载 + 拖动

**服务端本来就支持 Range** —— 这才是关键认知：卡顿不是协议问题，是**没预加载**。

| 层 | 改动 | 理由 |
|---|---|---|
| `conundrums/page.tsx` | `preload="metadata"` → **`auto`** | 挂载即完整缓存该集（单集 2-9MB、均 4.5MB）。上一轮为省带宽留 metadata，现在用户要拖动，必须换 |
| 同上 | 新增 `prefetchedRef` + useEffect，展开课题时插 `<link rel="prefetch" as="video">` | 低优先级抓取、不阻塞渲染、不触发播放器实例。**刻意不写 cleanup** —— 移除标签会让浏览器取消进行中的预取，白费带宽 |
| `nginx/studymate.conf` | 新增 `/videos/` location 直出 | 原先走 `location /` → Next.js，而 **Next.js 对 public/ 静态资源默认返回 `Cache-Control: max-age=0`**，每次播放都回源；叠加 `proxy_buffering off`，拖动反复触发缓冲 |

**Nginx location 三个必须记住的坑：**

1. **子 location 的 `add_header` 会覆盖父级** → COOP/COEP 必须重复声明
2. **不要写 `expires` 指令** → 它会自动生成 `Cache-Control`，与 `add_header Cache-Control` 同名头互相覆盖，最终生效哪条取决于书写顺序
3. **不要手工 `add_header Accept-Ranges bytes`** → nginx 静态模块自带，会**重复出现两次**（实测确认）
4. `try_files $uri =404` → 文件不存在必须 404，**不能回落成 HTML**（否则播放器解析失败）
5. 缓存策略：`Cache-Control: public, max-age=2592000, immutable`（文件名即课题 id，换片会换文件，30 天安全）

## 作品介绍视频支持拖动（同日，commit `961459a` + `3271ae2`）

### 用户反馈

作品详情页 `/camp/work/[slug]` 的「看看创作者怎么讲自己的作品」视频 → 「这里的视频也应该缓存播放」。

### 根因：服务端不支持 Range（不是缺预加载）

`frontend/app/api/camp/videos/[filename]/route.ts` **照抄了 covers 路由的写法**：

```ts
const buf = readFileSync(p);          // 整片读进内存
return new NextResponse(new Uint8Array(buf), {
  headers: { 'Accept-Ranges': 'bytes' },  // ← 声明支持分段
});
```

**声明了 `Accept-Ranges: bytes` 却完全无视 `Range` 请求头**，永远返回 200 全量。
浏览器拖进度条时无法请求「第 30 秒那段」，只能从头重新下载 → 拖不动。

> **关键判断**：封面图几百 KB 用 `readFileSync` 没问题（covers 路由是对的），
> **视频几十上百 MB 照抄这个模式就出事**。
> 教训：**复制粘贴相邻功能的实现时，先问「这个做法的前提在我的场景成立吗」。**
> 另外这也暴露一个隐患：100MB 文件整片进内存，**多人同看会吃满 Node 进程**。

### 一、路由重写（流式 + 完整 RFC 7233 Range）

`createReadStream` 流式响应 + 按 RFC 7233 实现 Range：

| 请求 | 响应 |
|---|---|
| 无 Range | 200 + `Content-Length` 全量流 |
| `bytes=a-b` | 206 + `Content-Range: bytes a-b/size` |
| `bytes=a-` | 206 至文件末尾 |
| `bytes=-n` | 206 最后 n 字节（起点 `size-n`）|
| end 超长 | 206 截断到 `size-1` |
| 起点越界 / start>end / 语法错 / `bytes=-0` | 416 + `Content-Range: bytes */size` |

### 二、详情页预加载

- `preload` 由 `metadata` → **`auto`**
- 新增 `videoSrc`（useMemo）+ 预取 `useEffect`：插 `<link rel="prefetch" as="video">`
- **只预取同源地址**（`videoSrc.startsWith('/')`）—— 外部直链的第三方服务器
  缓存头与 Range 行为不可控，强行预取会白耗用户流量
- 刻意不做 cleanup（移除标签会让浏览器取消进行中的预取）

### 三、nginx 直出（视频不经 Node 进程）

**前提发现**：`camp-videos` 原先落在**命名卷** `studymate-frontend-data` 的 `/app/data/camp-videos`，
**宿主机上无路径，nginx 读不到** → 必须先加绑定挂载。

- `docker-compose.yml`：新增 `./frontend/data/camp-videos:/app/data/camp-videos`
  （与 `classrooms` 同模式：先挂命名卷占住 `/app/data`，再把宿主机目录挂到子路径覆盖）
- `nginx/studymate.conf`：新增 `/api/camp/videos/` 直出 location

### ⚠️ nginx 陷阱：`alias` 在正则 location 与前缀 location 下行为不同

**实测（nginx:alpine 容器逐条验证）**：

```nginx
# ❌ 正则在 regex location 下，alias 是「整个匹配 URI 被替换」→ 文件名丢了 → 一律 404
location ~ ^/api/camp/videos/[a-zA-Z0-9-]+\.(mp4|webm|mov|m4v)$ {
    alias /data/camp-videos/;      # 404！
}
# 试过 alias /data/camp-videos/$1;  → 仍 404

# ❌ 嵌套正则 location 更糟：合法文件 404，穿越反而 200（爬到了 upstream）
location /api/camp/videos/ {
    location ~ ^...$ { alias /data/camp-videos/; try_files $uri =404; }
    try_files /__deny__ =404;
}

# ✅ 前缀 location + if 白名单（最终采用）
location /api/camp/videos/ {
    alias /home/ubuntu/studymate/frontend/data/camp-videos/;
    if ($request_uri !~ "^/api/camp/videos/[a-zA-Z0-9-]+\.(mp4|webm|mov|m4v)$") {
        return 404;
    }
    try_files $uri =404;
}
```

**要点**：
- **前缀 location 下的 alias 保留后续路径段**，路径拼接才正确
- 白名单用 **`$request_uri`（未解码原始值）** 而非 `$uri`，可挡 `%2e%2e%2f` 编码穿越
- 这是**必须实测**的配置 —— 光看语法 `nginx -t` 通过，行为却完全错

### 四、验证（全部真机实测）

**Range 分支 10/10 符合 RFC 7233**（独立 Node 服务逐条 curl）：

```
无 Range             → 200  Content-Length: 3122816
bytes=0-             → 206  0-3122815/3122816
bytes=1048576-2097151→ 206  Content-Length: 1048576（恰好 1MB）
bytes=-1024          → 206  3121792-3122815（=3122816-1024）
起点越界/start>end/语法错/bytes=-0 → 416 + bytes */3122816
end 超长             → 206  截断到 3122815
末尾区间 bytes=3122810- → 206  Content-Length: 6
```

**nginx location 实测**（逐字复刻生产配置）：

```
合法 mp4 → 200  video/mp4 + Accept-Ranges + Cache-Control + COOP/COEP
Range    → 206  Partial Content + Content-Range
bytes=-2048 → 206  起点 3120768（=3122816-2048）
不存在文件/非法后缀/子目录/空格文件名/大写后缀 → 全部 404
穿越变体（../、%2e%2e%2f、%252e%252e%252f、..%2f）
  → 全部落到 upstream NEXTJS_UPSTREAM 或 nginx 404，无一读到文件
```

**端到端（真实 Chrome，`arctic.mp4` 97.13s）—— 两条链路各跑一次**：

| 链路 | 整片缓存 | 四次跨段拖动耗时 | 媒体请求 |
|---|---|---|---|
| API 路由（Node 流式） | 100%（`buffered [0, 97.1]`） | 77 / 12 / 41 / 14 ms | 1 次 |
| nginx 直出 | 100%（`buffered [0, 97.1]`） | 40 / 13 / 36 / 14 ms | 1 次 |

两者均**四次拖动零回源**。

**写验证脚本时踩的坑（值得记）**：`verify_range.sh` 首版把 4 个 416 分支误判 `[FAIL]`。

```bash
# ❌ want_extra 含空格 → grep 收到两个 pattern，
#    且 `*/3122816` 的 `*` 前面没有可重复原子 → grep 报错返回非 0
echo "$hdr" | grep -q "$want_extra"

# ✅ 固定子串匹配
contains() { printf '%s' "$2" | grep -qiF -- "$1"; }
```

**反向验证的教训（重要）**：修完后不能只测「正常服务全绿」——那是断言写错时的"恒绿"陷阱。

**「能报错」和「能通过」同等重要。**

**另一个坑**：脚本探测端口前要先 `netstat -ano | grep <port>` 看有无旧实例。
上次会话残留的服务进程占着端口，新服务 `EADDRINUSE` 启动失败，
但**旧实例仍静静返回 200**（服务的是旧代码）→ 极易误判成"新代码生效"。

### 坑 1：TSV col1 含 `.pdf` + 脚本再拼 `.pdf` → 全部 89 个文件双扩展名（最后一个 404 的真因）

`gen_textbooks_meta.py` 写 TSV col1 是 `slug.pdf`，`upload_textbooks.sh` 又拼 `"$REMOTE_DIR/$slug.pdf"`
→ 服务器上全是 `biology-pep-g7a.pdf.pdf`。nginx 白名单、权限链（namei）、页面全部正确，就是文件名多一截。

- **应急**：`for f in *.pdf.pdf; do mv "$f" "${f%.pdf}"; done` → 89 个就位
- **根治**：脚本读入后 `slug="${slug%.pdf}"`，重跑验证 89/89 SKIP / 0 失败 / exit 0
- **教训：数据文件的列值自带扩展名时，写死再拼一次扩展名的脚本必然双击 —— 读取处剥一次最稳**

### 坑 2（本轮最大发现）：nginx conflicting server name 静默吞掉整个配置文件

`sites-enabled/default`（certbot 生成）与 `studymate.conf` **都声明 `aijiangti.cn:80`**。
nginx 按字母序加载，`default` 先到 → **studymate.conf 的 server 块被整体忽略**，
`nginx -t` 只给 warning 不报错。

**后果**：此前 `/videos/` 与 `/api/camp/videos/` 直出**从未真正生效过**，全部走了 Next.js 代理
（代码没问题，是配置从没被加载）。真实生产布局：80 端口仅 301 跳 https；443 SSL 块承载全部业务
（证书 `/etc/letsencrypt/live/aijiangti.cn/`、SAN 覆盖 aijiangti.cn + www）。

- **修复**：移除 `sites-enabled/default` 符号链接（备份 `default.bak-20260915`）+ 重写 studymate.conf 为 80/443 完整布局 + reload（无 conflicting 警告）
- **副产品**：`/videos/` 课题视频直出**首次真正生效**（200 video/mp4 + 30d immutable + Accept-Ranges）
- **教训：新增 location「不生效」且行为像走了 upstream 时，先查是否有第二个文件声明了相同 `server_name:port`**

### 坑 3：沙箱 curl 被代理劫持，本地全量验证必然假失败

本机 curl 被 `http_proxy=127.0.0.1:63962` 劫持，`no_proxy='*'` 与 `--noproxy` 均无效
→ 本地跑 89 条全量 HEAD 得 **89/89 全部 000（假失败）**。**可靠路径：ssh 到服务器内用 curl，
