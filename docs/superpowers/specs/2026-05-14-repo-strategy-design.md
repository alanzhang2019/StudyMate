# AI-MATH-MISTAKE 仓库策略设计

> 目标：明确 `AI错题讲解机` 是否应建立新仓库，还是在 `AI-MATH-MISTAKE` fork 基础上继续二开。
> 日期：`2026-05-14`
> 结论类型：仓库继承与改造策略

## 结论

采用：

`以 AI-MATH-MISTAKE 为主仓库继续二开，不重新建立新仓库`

这是在当前约束下的推荐方案：

- 用户优先级为 `最快起步`
- 用户可接受的改造强度为 `轻改 Fork`
- 项目目标是尽快跑通 `AI错题讲解机` 的闭环 MVP，而不是先做仓库洁癖式重构

## 为什么不建议现在新建仓库

如果现在新建仓库，虽然边界更干净，但会立即带来以下成本：

- 重新搭建基础目录与工程壳
- 重新接 provider abstraction
- 重新接 workflow infrastructure
- 重新处理部署与配置
- 重新建立已有可复用的工程约定

这些工作对当前 MVP 的核心价值贡献很低。

当前阶段真正重要的是：

- 快速建立错题诊断闭环
- 让拍题/录题、诊断、讲解、验证题、错题本、家长报告尽快形成可评估链路

因此，重新建仓库不符合当前的速度目标。

## 为什么推荐在 Fork 上二开

`AI-MATH-MISTAKE` 已经是你 fork 并改名后的仓库，这意味着：

- 仓库入口已经存在
- 后续演进路径更连续
- 工程底座可以直接复用
- 团队协作和远端管理成本更低

更重要的是，这个项目与 `OpenMAIC` 不是“完全无关”，而是：

`产品形态不同，但底层工程基础有复用价值`

因此更合适的做法不是“完全切断”，而是：

`保留工程底座，重建核心学习引擎`

## 仓库继承原则

以 fork 仓库为基础二开，不等于照搬原产品。

本项目应遵循以下继承原则：

1. 复用工程基础，不复用课堂产品假设
2. 复用基础设施层，不复用原有核心业务闭环
3. 先旁路不适配模块，再逐步替换，而不是一开始全面大拆
4. 优先保证 MVP 跑通，再做更彻底的去 OpenMAIC 化

## 哪些层应该保留

### 直接保留

这些通常可以直接复用：

- web shell
- provider abstraction
- 基础 workflow infrastructure
- config / env / deployment 基础
- 通用工具函数

这些内容的价值在于：

- 它们能显著缩短启动时间
- 它们与课堂产品形态耦合较低
- 它们不决定错题产品的业务方向

### 保留但尽快隔离

这些内容可能能复用，但需要小心隔离：

- 路由组织结构
- 持久化适配层
- streaming orchestration patterns
- 一些共享服务层

原则是：

- 如果它们不强依赖原来的课堂语义，可以短期保留
- 如果命名或边界已经明显带有课堂心智，应尽快包一层或替换

## 哪些层不应该继续沿用

以下内容不应成为 `AI错题讲解机` 的产品基础：

- 课堂生成型主工作流
- 长链路教学或课程生成逻辑
- 互动课堂、讨论、表演式多 agent 教学结构
- 把产品默认理解成“通用 AI 家教”的对话形态
- 为课堂内容生产服务的复杂编排

这些内容的问题不是“不能运行”，而是：

- 会把产品带偏
- 会拖慢 MVP
- 会让诊断引擎被错误的业务抽象包裹

## 建议的改造方式

推荐采用：

`轻改 Fork + 逐步旁路旧核心业务`

而不是：

`大规模先拆后建`

### 第一阶段

目标：尽快跑起来

- 保留仓库骨架
- 保留通用基础层
- 新建错题诊断相关目录和工作流
- 让 MVP 主链路先独立可运行

### 第二阶段

目标：减少历史包袱

- 逐步旁路不再使用的课堂路由和页面
- 把仍然需要的基础模块抽成更中性的命名和边界
- 降低核心业务对旧产品结构的依赖

### 第三阶段

目标：视验证结果决定是否进一步去 OpenMAIC 化

- 如果产品验证很好，再考虑更彻底地重构目录与命名
- 如果团队规模扩大，再考虑是否在那时拆出更纯净的新仓库

## 对 MVP 的直接好处

采用 fork 二开方案，对当前 MVP 有三个直接好处：

1. 起步快
2. 工程风险低
3. 能把主要精力放在错因诊断与评估闭环上

这与项目当前真正要验证的东西一致：

- 学生是否更容易改正一类错误
- 家长是否能看懂价值
- 系统是否能形成可评估的短闭环

## 风险与控制方法

### 风险 1：遗留命名和目录污染心智

控制方法：

- 新业务目录优先使用 `mistake`, `diagnosis`, `practice`, `parent-report` 等中性命名
- 新核心工作流不复用课堂业务命名

### 风险 2：旧工作流被误复用

控制方法：

- 在设计与代码评审中明确区分“基础设施复用”和“业务闭环复用”
- 对课堂生成相关链路默认持保守态度

### 风险 3：后续越改越乱

控制方法：

- 先把 MVP 主链路独立出来
- 后续只围绕主链路做增量重构
- 不在早期同时推动大规模目录清洗

## 验收标准

这项仓库策略应满足以下标准：

1. 能在现有 fork 上快速启动开发
2. 不强依赖 `OpenMAIC` 的课堂产品结构
3. 能支持 `AI错题讲解机` 的专属诊断闭环
4. 后续仍有空间逐步去 OpenMAIC 化

## 推荐下一步

基于这个仓库策略，下一步最值得做的是：

1. 盘点 `AI-MATH-MISTAKE` 中哪些模块属于 `直接保留 / 保留但隔离 / 不继续沿用`
2. 画出 `AI错题讲解机` 的第一版目录映射
3. 再进入具体的迁移或开发计划
